# Tests

A mocked-Firebase test suite for Orford Live, so "does anything still work?" can be answered
without touching the real database, and without needing to rebuild it from scratch in a future
Claude session or when you (or someone else) edits this code by hand.

## Important: this is NOT tested against your real data

Every test here runs against a **fake, hand-written set of sample trails/shelters/inspections**
(`mock.html`) - never the real Firestore database, and no login is ever used. That mock covers the
shapes of data the app needs to handle (old-format records, both networks, both ski kinds,
archived trails, etc.) but it is not a substitute for actually using the app with real data as a
real logged-in user.

## How to run it

```powershell
cd tests
.\run.ps1              # everything
.\run.ps1 -Quiet        # everything, only print failures + totals
.\run.ps1 -Only kind,mapservice,trailservice   # just these (see names below)
```

Requires: Windows PowerShell and Microsoft Edge at the default install path (edit `$edge` near
the top of `run.ps1` if yours is somewhere else). Nothing else - no Node, no npm, no build tools.
`run.ps1` starts a throwaway local web server on port 8765, builds each test page under
`_build\` (gitignored - safe to delete, regenerated every run), drives headless Edge against it,
and prints a `PASS`/`FAIL` line per assertion plus a total.

If a test intermittently shows `NO OUTPUT` or `0 pass, 1 fail`, it's very likely a timing flake
(the page needed more than the default time budget to finish rendering before Edge dumped the
DOM) - retry with `-Budget 20000` or so, not a sign of a real bug.

## What's in here

| File / folder | What it is |
|---|---|
| `run.ps1` | The test runner (build + serve + drive Edge + report). Run this. |
| `_server.ps1` | A tiny static file server `run.ps1` starts as a child process. Not run by hand. |
| `mock.html` | The fake Firebase: sample data, a fake `checkAuthStatus`/`db`/`firebase.*`, and `window.__writes`/`window.__reads`/`window.__reloads` so tests can check what a page tried to save/read/reload without it actually happening. |
| `specs/*.html` | The actual assertions, one file per group of pages (see the table below). Each is just a `<script>` that runs after the real page + mock have loaded, and writes `PASS ...` / `FAIL ...` lines into a `<pre id="out">`. |
| `_build/` | Generated by `run.ps1` (real page + mock + spec, glued together). Gitignored. |

## Météo: what the tests cannot prove - try these on the real site

The tests play Firebase and Environment Canada with a simulated version of each. After deploying the pages and
publishing `assets/Rules for Firebase.txt`, try this (about 10 minutes). Tell me what you see if a step differs.

| # | Do | Expected |
|---|---|---|
| 1 | Administration > Utilisateurs: tick **Météo** on your own profile, then open the portal. | A yellow **Météo** tile (snowflake in the ski season, sun in the bike season). |
| 2 | Open Météo > Relevés. Click **Charger les données d'Environnement Canada**. | Values appear beside empty "Votre valeur" boxes: temperature, humidity, wind and gusts from *Lac Memphrémagog*, pressure / clouds / visibility marked *aéroport de Sherbrooke (estimation)*, a feels-like marked *calculée*, with the time of the observation. | 3 | Type a snow depth and a fresh-snow value, add a comment, **Enregistrer**. | A green notice "Relevé enregistré.", the form empties, the reading is in the day's list with ✎ (typed) and 🌐 (web) marks. |

| 8 | Météo > Admin > Statistiques, with a few days of readings. | Cards and three charts (temperature, fresh snow, snow at the base): one value per day, the reading closest to noon; "Jours sans relevé" counts the last 20 days before today. |

## The volunteer limits: what the tests cannot prove

`volunteer-limits.html` runs the page logic against a JavaScript transcription of the rules
(`volStateOk` / `volWindowOk` / the `volunteers` create rule in `assets/Rules for Firebase.txt`). It
cannot run the REAL rules: after republishing them, try these in the Firebase console, Rules
Playground (simulation type "create"/"update", **unauthenticated**, unless noted). The console also
refuses to publish rules with a syntax error - read its message if it does.

1. Batch-free checks cannot be simulated in the Playground (it tests one document at a time with the
   state "after" the batch not available), so verify the whole path on the real page: register one
   volunteer -> Administration > Bénévoles shows "1 / 10" for the minute and the volunteer in the list.
2. Register 11 times within a minute (use the page, different names): the 11th shows
   "Trop d'inscriptions en peu de temps...". A minute later it works again.
3. Administration > Bénévoles: set "Par minute" to 1, save, register twice: the second is refused;
   restore 10. Untick "Inscriptions ouvertes": the public page shows the closed notice; tick it again.
4. "Réinitialiser les compteurs" sets everything back to 0 (the volunteers stay).
5. Playground, unauthenticated: `create` on `/volunteers/test1` with valid fields and NO counters
   change -> must be **denied**. `update` on `/volunteerLimits/config` -> **denied**. `get` on
   `/volunteerLimits/state` -> allowed.
6. If registrations are refused for everybody right after publishing, the rules text is the suspect:
   restore the previous version from the Firebase console (Rules > history) and report what the page
   and the browser console said.

## Adding a test

- A new assertion for something already covered: add an `ok('description', condition, debugValue)`
  line to the relevant `specs/*.html` file (see the existing ones for the pattern - `ok` pushes a
  `PASS`/`FAIL` line; the third argument is only shown on failure, for debugging).
- A new page or spec pairing: add an entry to the `$tests` array near the top of `run.ps1`
  (`type: 'page'` needs a real page + a spec + the URL query strings to try; `type: 'unit'` is a
  spec that stands alone).
- `window.confirm`/`window.alert` must stay the browser's real, synchronous ones (this was a real
  bug once - see the app's own memory notes) - specs that trigger a confirm-guarded action stub
  `window.confirm = () => true` first, and several specs assert they're still native as a
  permanent regression guard.

# Tests

A mocked-Firebase test suite for Orford Live, so "does anything still work?" can be answered
without touching the real database, and without needing to rebuild it from scratch in a future
Claude session or when you (or someone else) edits this code by hand.

## Important: this is NOT tested against your real data

Every test here runs against a **fake, hand-written set of sample trails/shelters/inspections**
(`mock.html`) - never the real Firestore database, and no login is ever used. That mock covers the
shapes of data the app needs to handle (old-format records, both networks, both ski kinds,
archived trails, etc.) but it is not a substitute for actually using the app with real data as a
real logged-in user.

## How to run it

```powershell
cd tests
.\run.ps1              # everything
.\run.ps1 -Quiet        # everything, only print failures + totals
.\run.ps1 -Only kind,mapservice,trailservice   # just these (see names below)
```

Requires: Windows PowerShell and Microsoft Edge at the default install path (edit `$edge` near
the top of `run.ps1` if yours is somewhere else). Nothing else - no Node, no npm, no build tools.
`run.ps1` starts a throwaway local web server on port 8765, builds each test page under
`_build\` (gitignored - safe to delete, regenerated every run), drives headless Edge against it,
and prints a `PASS`/`FAIL` line per assertion plus a total.

If a test intermittently shows `NO OUTPUT` or `0 pass, 1 fail`, it's very likely a timing flake
(the page needed more than the default time budget to finish rendering before Edge dumped the
DOM) - retry with `-Budget 20000` or so, not a sign of a real bug.

## What's in here

| File / folder | What it is |
|---|---|
| `run.ps1` | The test runner (build + serve + drive Edge + report). Run this. |
| `_server.ps1` | A tiny static file server `run.ps1` starts as a child process. Not run by hand. |
| `mock.html` | The fake Firebase: sample data, a fake `checkAuthStatus`/`db`/`firebase.*`, and `window.__writes`/`window.__reads`/`window.__reloads` so tests can check what a page tried to save/read/reload without it actually happening. |
| `specs/*.html` | The actual assertions, one file per group of pages (see the table below). Each is just a `<script>` that runs after the real page + mock have loaded, and writes `PASS ...` / `FAIL ...` lines into a `<pre id="out">`. |
| `_build/` | Generated by `run.ps1` (real page + mock + spec, glued together). Gitignored. |

## Which spec covers which pages

| Spec | Pages it's run against | What it checks |
|---|---|---|
| `specs/smoke.html` | `index.html`, `support.html`, `user-profile.html`, `user-management.html` | Basic load, branding, nav, no script errors. |
| `specs/sector-apps.html` | `infraction-report/admin.html`, `signalisation-report/admin/resume.html` | Sector/trail pickers, old vs. new report formats, the shared photo-location pop-up (map switch, calibration states). |
| `specs/inspection.html` | `inspection-dashboard/trail-report/shelter-report/history/admin.html` | The whole inspection app: network + kind (Montée/Descente) scoping, the header switchers, issue checklists, quick status changes, the season navigator, "Gestion des données" text. |
| `specs/maps.html` | `user-management.html` (Cartes tab) | GPS calibration (affine + perspective fits) for all 3 maps. |
| `specs/trails.html` | `user-management.html` (Sentiers tab) | Trail CRUD, sector assignment, hide/restore, click-to-place positioning. |
| `specs/trailservice.html` | none (loads `js/core/*.js` directly) | `TrailService` unit tests: kinds, difficulties, status/condition wording, issue lists. |
| `specs/mapservice.html` | none (loads `js/core/*.js` directly) | `MapService` unit tests: the affine/perspective GPS math, calibration save/load. |
| `specs/kind.html` | none (loads `js/core/*.js` directly) | `Kind` (the Montée/Descente switcher's state) unit tests: defaults, persistence, per-network isolation. |

## Adding a test

- A new assertion for something already covered: add an `ok('description', condition, debugValue)`
  line to the relevant `specs/*.html` file (see the existing ones for the pattern - `ok` pushes a
  `PASS`/`FAIL` line; the third argument is only shown on failure, for debugging).
- A new page or spec pairing: add an entry to the `$tests` array near the top of `run.ps1`
  (`type: 'page'` needs a real page + a spec + the URL query strings to try; `type: 'unit'` is a
  spec that stands alone).
- `window.confirm`/`window.alert` must stay the browser's real, synchronous ones (this was a real
  bug once - see the app's own memory notes) - specs that trigger a confirm-guarded action stub
  `window.confirm = () => true` first, and several specs assert they're still native as a
  permanent regression guard.
